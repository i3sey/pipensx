# Зонд sysmodule

Отвечает на железе на гипотезы, на которых стоит разворот «приложение —
каталог, движок — демон, прогресс — в оверлее» (`docs/plans/SYSMODULE_PLAN.md`,
`docs/plans/ESHOP_APPLET_PLAN.md` §5). Движок в зонд намеренно не линкуется.

| # | Гипотеза | Где смотреть в отчёте |
|---|---|---|
| H1 | потоки homebrew получают CPU в half-awake | есть ли сэмплы с `rtc` **внутри** окна сна |
| H2 | байты ходят по сети во сне | растут ли `rx0..rx3` в этих сэмплах |
| H2b | во сне живёт больше одного сокета | `rx0` (сокет зарегистрирован в nifm) против `rx1..rx3` |
| H3 | psc даёт сон/пробуждение и ack не вешает консоль | строки `psc state=` в событиях |
| H4 | `bgtc:t` доступен | `bgtc:t open rc=`, `EnableStayHalfAwake rc=`, бит `half_awake` во `flags` |
| H5 | bsd/fsdev/csrng работают вне апплета | строка `init fs=… socket=… csrng=…` |
| H6 | фон не убивает игру | скорость по `rx*` под игрой против покоя |
| H7 | цена в SYSTEM-пуле | `heap_used` + строка `static heap=… ring=… report=…` |
| H8 | TCP между процессами | `loopback in-process …` + вердикт `pipensx-probe-client.nro` |

## Сборка

```
make probe
```

Отдельная цель, а не часть `make switch`: зонд — исследовательский артефакт и в
релизный путь приложения не входит.

Кладёт:

```
build-switch/probe/atmosphere/contents/00FF0000504E5358/exefs.nsp
build-switch/probe/atmosphere/contents/00FF0000504E5358/toolbox.json
build-switch/probe/switch/pipensx-probe-client.nro
```

Скопировать содержимое `build-switch/probe/` в корень SD.

## Запуск

**`boot2.flag` не кладётся намеренно.** Модуль запускается в рантайме —
`ovl-sysmodules` (Tesla) или любой инструмент поверх `pm:shell`. Так зависший
зонд не может помешать консоли загрузиться. Аварийный выход в любом случае:
удалить `atmosphere/contents/00FF0000504E5358/` с SD на ПК.

Один контрольный прогон под `boot2.flag` имеет смысл в самом конце — убедиться,
что запуск демоном boot2 не отличается от запуска через `pm:shell`.

## Конфиг

`sdmc:/switch/pipensx/probe.ini`, читается один раз при старте:

```ini
host = 192.168.1.1        # IP предпочтительнее имени: убирает DNS из переменных
path = /1GB.zip
port = 80
report_port = 8099
net_threads = 4           # 0 — выключить сетевую нагрузку
psc = 0                   # см. предупреждение ниже
bgtc = 1
bgtc_stay = 1             # EnableStayHalfAwake
bgtc_task = 1             # NotifyTaskStarting
bgtc_schedule = 0         # ScheduleTask(N секунд); 0 — не звать вовсе
kept_in_sleep = 1
kept_socket = 1           # регистрация сокета 0 под WoWLAN — это не то же самое
load_in_sleep_only = 0    # 1 — качать только внутри окон half-awake
loopback = 1
run_seconds = 0           # 0 — до принудительной остановки
```

`load_in_sleep_only = 1` нужен суточным прогонам: иначе зонд тянет на линейной
скорости все часы бодрствования, а это не измеряет ничего и изнашивает раздачу
с картой. Требует `bgtc = 1` — ворота открывает опрос `IsInHalfAwake`.

Суточный прогон читается не по кольцу сэмплов (1800 штук — это полчаса), а по
строкам `gap #N` в журнале: сэмплер получает CPU только когда его планируют,
поэтому скачок часов и есть граница окна. Журнал вытесняет старые строки, кроме
закреплённых строк старта, так что хвост суток доживает.

`bgtc = 0` выключает всё, включая опрос `IsInHalfAwake`, — тогда окна не видны
вообще. Чтобы **наблюдать** окна, ничего не заказывая, нужно `bgtc = 1` при
всех трёх ключах в нуле.

Эти три ключа отвечают на вопрос №1 из `SYSMODULE_PROBE_RESULTS.md` §7: окна
даёт система сама или их заказала наша задача? В прогоне 2026-07-29 все три
вызова шли вместе, и интервалы 20–113 с подозрительно совпали с запрошенными
`ScheduleTask(60)`. Три прогона разводят это:

| прогон | `bgtc_stay` | `bgtc_task` | `bgtc_schedule` | что проверяет |
|---|---|---|---|---|
| 1 | 0 | 0 | 0 | есть ли окна вообще без наших запросов |
| 2 | 1 | 0 | 0 | достаточно ли одного «stay» |
| 3 | 1 | 0 | 30 | следует ли интервал за заказанным числом |

Если третий двигает интервал — демон умеет **заказывать** окна, и потолок
скорости во сне становится ручкой, а не константой.

> `psc=0` по умолчанию не случайно: зарегистрированный psc-модуль, который не
> подтвердил переход, задерживает засыпание всей консоли. Первый прогон E2 —
> с `psc=0`, чтобы сон заведомо не сломался; включать после того, как стало
> ясно, что зонд жив.

## Снятие результатов

```
curl http://<ip-консоли>:8099/       # весь отчёт
curl http://<ip-консоли>:8099/ping   # жив ли зонд
```

Дубль — `sdmc:/switch/pipensx/probe-report.txt`, пишется раз в 30 с и сразу
после пробуждения. Сэмплы копятся в RAM, а не пишутся построчно: во сне `fs`
может быть недоступна, и потерять записи именно там было бы бессмысленно.

Формат: сначала события (`# events`), потом CSV
`tick,rtc,heap_used,flags,psc_state,sock_alive,rx0,rx1,rx2,rx3`.
`flags`: 1 half-awake, 2 сеть поднята, 4 KeptInSleep принят, 8 первый сэмпл
после пробуждения.

Пара `tick`/`rtc` — главный различитель. Дыра в `rtc` при непрерывном `tick` и
дыра в обоих — разные диагнозы, и путать их нельзя.

## Матрица экспериментов

| # | Что делаем | Что закрывает |
|---|---|---|
| E1 | 5 мин покоя в HOME-меню | H5, H7, базовая скорость |
| E2 | **сон 10 мин кнопкой, затем пробуждение** | H1, H2, H2b, H3, H4 |
| E3 | 10 мин с запущенной игрой | H6 |
| E4 | сон из игры, 10 мин | H1 в реальном сценарии |
| E5 | док/андок, обрыв Wi-Fi | устойчивость psc/nifm |
| E6 | `pipensx-probe-client.nro` из hbmenu, пока зонд работает | H8 |

Перед E1 — контрольный замер того же URL с ПК в той же сети, иначе медленный
хост будет выглядеть как отказ bsd.

Критерий готовности — не «зонд работает», а «каждая строка таблицы решений в
плане получила однозначный исход».
