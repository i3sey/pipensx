# GBA: HOME-forwarder

2026-11-16. Реализация на ветке `feat/retro-gba`. Это описание формата и
проверок нового этапа, а не подтверждение запуска нового ярлыка на консоли.

## Формат и компоненты

Используется имеющийся in-memory NSP builder из
[`vendor/autorun-forwarder`](../../vendor/autorun-forwarder/README.md).
Происхождение: autorunhq/autorun commit
`1ac9b6cf37b90f2d5783dd7ef389bebbe1c68877`, файлы
`horizon-wine/source/forwarder.c`, `low_window.h`, `horizon-wine/hbl/`.
Лицензии остаются в vendor. Loader NSO и NPDM собираются существующей целью
CMake `autorun_forwarder`; сторонние готовые NSP не скачиваются.

NSP содержит Program, Control и Meta NCA с application metadata версии 0.
Loader читает RomFS `nextNroPath` и `nextArgv`:

- NRO: `sdmc:/switch/mGBA/mGBA.nro`.
- Аргументы: `"sdmc:/switch/mGBA/mGBA.nro" "sdmc:/…/game.gba"`.
- Контракт кавычек, кириллицы и пробела ранее проверен прямым запуском из
  библиотеки в mGBA 0.10.5. Запуск отдельного HOME-ярлыка требует новой проверки.
- Имя берётся из записи игры, обрезается до 511 байт на границе UTF8 для NACP.
- Publisher нового варианта builder: `pipensx Retro`. Старый вызов AutoRun
  сохранён как wrapper с прежним publisher `AutoRun / pipensx`.
- Значок: существующий `resources/icon.jpg` pipensx, уже включённый в RomFS
  как `autorun-icon.jpg`. Собственные картинки не создаются. Обложки конкретных
  ROM пока не подключены; интерфейс явно называет используемый значок.

## Идентификатор и конфликты

Игровая идентичность остаётся `gba-<topic>:<SHA256 относительного пути ROM>`.
Имя игры не участвует в выборе application ID. Для каждого game ID SHA256 от
`gameId + ":" + probe` даёт 27 бит; они сдвигаются на 13 бит и объединяются
с префиксом `0100D7`. Кандидаты выровнены на `0x2000`, чтобы application,
patch и DLC не делили низкие биты. До 32 кандидатов. Это локальная политика,
не обещание уникальности префикса среди всех существующих Switch-приложений.

Перед выбором проверяются сохранённые резервации других игр, полный список
NS-приложений и NCM metadata диапазона ID…ID+0x1fff в SD и BuiltInUser.
Неудачная/неполная проверка прерывает операцию; занятой кандидат не используется.
Резервации сохраняются и после удаления ярлыка, поэтому повторное создание
той же игры использует прежний application ID. Совпадения названий разных
игр не объединяют их ярлыки.

## Владение и восстановление

Файл `retro/forwarders/<SHA256 game ID>.json`, format 1, хранит game ID,
application ID и два отпечатка: текущий и предыдущий. Отпечаток состоит из
Program Content ID + Control Content ID. Имя/publisher не доказывают владение.
При идентификации собственного установленного ярлыка допускается только один
SD application meta версии 0, наличие Program/Control в content storage и
соответствие сохранённым Content ID. Дополнительные/чужие записи или отсутствие
обязательного content приводят к отказу от удаления/замены.

Перед изменением NCM записывается намерение с новым отпечатком и предыдущим
живым отпечатком. Файл ограничен 16 КиБ, записывается во временный файл с fsync
и rename; есть `.previous` для восстановления. Чтение и запись через symlink-файлы/родители
отклоняются. Повреждённый primary не заменяет последний читаемый backup.
Нет утверждения о проверенной устойчивости FAT к внезапному отключению питания.

Повторная генерация идентичного пакета проверяет установленный отпечаток и
не добавляет новое приложение. Если пакет изменился, повторно проверяется
владение, удаляется только связанный ярлык и устанавливается новый под тем же
ID. Это необходимо, потому что существующий backend при наличии той же
metadata version считает пакет уже установленным. При отказе установки игра
остаётся в библиотеке; намерение позволяет повторить операцию после частичного
сбоя, включая потерю ответа после успешного commit. Атомарной замены ярлыка без
интервала отсутствия здесь нет. Неполные NS/NCM-состояния (например, metadata
без NS-записи или без content) не чинятся автоматически: сервис отказывает
до отдельного восстановления/очистки. Отсутствующие/переустановленные вне pipensx
приложения проверяются заново при каждом действии.

Установка выполняется через существующий InstallBackend на SD. Проверяются
границы PFS0, три файла NCA и соответствие SHA256 имён содержимому. Перед commit
проверяется application ID пакета, после commit повторно читаются NS/NCM.
Удаление использует `nsDeleteApplicationCompletely` только после проверки
сохранённых Content ID и ещё одной проверки непосредственно перед вызовом.
Это удаляет ярлык; ROM, архивы, сохранения и конфигурация mGBA лежат отдельно
и не удаляются. Внешний установщик не разделяет mutex pipensx: межпроцессной
атомарной блокировки NS/NCM этот сервис не заявляет.

## Интерфейс и ограничения

В деталях игры доступны создание/обновление и удаление HOME-ярлыка, оба с
подтверждением. При удалении записи доступны «Только запись» и «Запись и ярлык
HOME». Если совместное удаление ярлыка не удалось, запись не удаляется.
Удаление записи отдельно оставляет связь ярлыка для повторного добавления игры.
Ошибка ярлыка показана отдельно; ROM и сохранения остаются.

На время операций используется существующий барьер DownloadManager
`beginSystemCleanup`/`endSystemCleanup`; активные/очередные передачи требуется
приостановить. Изменяющие кнопки выключены и игнорируют touch, фокус переводится
на «Закрыть». Закрытие экрана не прерывает уже начатую операцию NCM; receipt
сохраняется независимо от времени жизни UI. «Мои игры» может потребовать
обычного обновления списка после установки.

mGBA пока единственный локальный профиль. Смена на другой эмулятор станет
доступна после отдельной проверки его launch-контракта; текущий механизм
отпечатков допускает обновление содержимого под прежним ID. Покрытие всех
ZIP/7z/RAR и torrent/debrid на физическом Switch относится к отдельному этапу.
