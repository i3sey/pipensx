# Зонд sysmodule: результаты замеров на железе

**Дата:** 2026-07-29. **Железо:** Nintendo Switch, Atmosphère, HOS 22.5.0.
**Инструмент:** `src/probe/` (`make probe`), отчёт по HTTP с самой консоли.

Этот документ — не план, а **протокол измерений**. Он опровергает
`SYSMODULE_PLAN.md` §0.3 и уточняет `ESHOP_APPLET_PLAN.md` §5.4; в спорных
местах авторитетен он, потому что стоит на цифрах, а не на рассуждении.

## 2. Загрузка во сне: цифры

Сон 10 минут, четыре качающих потока, plain-HTTP GET с ПК в той же сети.

```
HALF-AWAKE  14s  rx+34.9 MiB   sock=14
awake        5s  rx+ 0.0
HALF-AWAKE  14s  rx+34.1 MiB   sock=14
awake       38s  rx+ 0.0
HALF-AWAKE  13s  rx+20.9 MiB   sock=14
...  всего 9 окон
```

- Длина окна: **15 с** (14–16, девять окон подряд).
- Интервал между началами окон: 20, 54, 20, 48, 46, 113, 26, 99 с — плавает.
- Внутри окна: **~2.4 MB/s** (в бодрствовании на том же источнике 9.9 MB/s).
- За 441 с сна: **282 MiB**, в среднем 0.64 MB/s → **~2.3 ГБ/час**, за ночь
  порядка 18 ГБ.

Разделитель, ради которого зонд пишет пару `tick`/`rtc`: на дырах `dTICK`
совпадает с `dRTC`. `armGetSystemTick()` продолжает считать во сне — по нему
можно мерить длительность сна, но не жизнь потоков.

### Живучесть сокетов

`sock_alive` в окнах равен **14** — потоки 1, 2, 3. Поток 0 мёртв. Именно он и
только он зарегистрирован через `nifmRequestSetKeptInSleep` +
`socketNifmRequestRegisterSocketDescriptor`; после пробуждения он застревает на
`nifm register state=1 errno=114`.

Причина в том, что `SetKeptInSleep` — **не механизм загрузки**. Switchbrew: при
засыпании `wlan:inf` cmd 19 `SetTcpSessionInformation` получает данные
зарегистрированных сокетов, то есть TCP keep-alive выгружается в прошивку
Wi-Fi-чипа (WoWLAN). Соединение переживает сон, трафик — нет. Для скачивания
эта регистрация вредна, и в демоне её быть не должно.

### Запись во сне (H9, E7)

```
HALF-AWAKE  14s   rx+25.2 MiB   sd+38.4 MiB
awake       55s   rx+ 0.0       sd+ 6.7 MiB
HALF-AWAKE  14s   rx+26.3 MiB   sd+40.2 MiB
awake       21s   rx+ 0.0       sd+ 3.6 MiB
HALF-AWAKE  14s   rx+26.6 MiB   sd+40.6 MiB
awake      339s   rx+ 0.0       sd+ 3.5 MiB
HALF-AWAKE  14s   rx+22.6 MiB   sd+41.1 MiB
```

- В окне: **~2.9 MB/s**, ~40 MiB — быстрее, чем приходит сеть (25 MiB за окно).
- **Вне окон fs доступна, а сеть нет.** В промежутке 339 с сеть стоит намертво,
  а на карту капает 3.5 MiB. Микро-окна CPU между окнами half-awake годятся,
  чтобы догонять запись уже скачанного.

Проверялся `fsdev`/SD, **не `ncm`**. Установка на NAND через content storage —
отдельный вопрос, зондом туда не лезли.

### Поправка к §2

`sock_alive` остался 14 и после того, как `kept_in_sleep` выключили. Значит
поток 0 отваливается **не** из-за WoWLAN-регистрации: три сокета из четырёх
восстанавливаются внутри окна, четвёртый не успевает, причина не установлена.
Вывод «`SetKeptInSleep` бесполезен для загрузки» остаётся в силе, атрибуция
мёртвого сокета — нет.

## 3. Обязательное условие: `enable_halfawake`

```ini
[bgtc]
enable_halfawake=u32!0x1
minimum_interval_normal=u32!0x4b0
minimum_interval_save=u32!0x15180
battery_threshold_save=u32!0x14
battery_threshold_stop=u32!0x14
```

Это заводские значения. На консоли, где ставился зонд, было
`enable_halfawake=0x0`, `battery_threshold_save/stop=0x64` (порог 100 % = режим
«стоп» всегда) и `minimum_interval_*=0x7FFFFFFF` — типовой anti-telemetry пакет,
рядом с заглушёнными `npns`, `ns.notification`, `prepo`, `olsc`,
`account.daemon`.

**Три первых теста сна мерили консоль, которой запрещено проверяемое.** Вывод
«загрузка во сне невозможна» был бы ложным, и именно он чуть не попал в план.

Индикатор для рантайма: `GetOperationMode` (cmd 101 на `ITaskService`) даёт
**3** когда фон заглушён и **0** когда разрешён; значение меняется сразу после
перезагрузки с новым `system_settings.ini`. Демон обязан проверять это на старте
и говорить пользователю прямым текстом, а не молча не качать.

Отдельно: правка `[bgtc]` **не** трогает блокировку телеметрии. Half-awake —
локальный планировщик фоновых задач, он сам по себе никуда не ходит.

## 4. bgtc: правильная форма вызовов

Трижды получали ложный отрицательный результат, пока не сверились со
switchbrew. Здесь — то, что стоило этих прогонов.

### `bgtc:t` — только корневой интерфейс

`nn::bgtc::ITaskServiceRoot` [11.0.0+] c единственной командой
**100 `CreateTaskService`**. Слепой свип нашёл её («отвечает только cmd 100») и
выбросил возвращённый объект. Всё интересное — на нём:

| Cmd | Имя | Прошивка |
|---|---|---|
| 1 | NotifyTaskStarting | |
| 2 | NotifyTaskFinished | |
| 3 | GetTriggerEvent | |
| 4 | **IsInHalfAwake** | |
| 5 | NotifyClientName | |
| 6 | IsInFullAwake | 3.0.0+ |
| 11–16 | ScheduleTask / GetScheduledTaskInterval / UnscheduleTask / GetScheduleEvent / SchedulePeriodicTask / ScheduleStrictTask | 16 — 9.0.0+ |
| 101 | GetOperationMode | 3.0.0+ |
| 102 | WillDisconnectNetworkWhenEnteringSleep | 3.0.0+ |
| 103 | WillStayHalfAwakeInsteadSleep | 3.0.0+ |
| 200 | EnableStayHalfAwake | 12.0.0+ |

### `bgtc:sc` — другой интерфейс с другой таблицей

`nn::bgtc::IStateControlService`: 1 `GetState`, 2 `GetStateChangedEvent`,
3 `NotifyEnteringHalfAwake` (с [10.0.0+] берёт 1 байт), 4
**`NotifyLeavingHalfAwake`**.

Первый прогон дёргал «cmd 4» раз в секунду, считая его `IsInHalfAwake` — то есть
весь тест сна сообщал системе «выхожу из half-awake». Read-only там только
`GetState`.

`bgtc:se` не существует.

### Сигнатуры, установленные перебором

- `NotifyClientName` принимает **HipcPointer-буфер** (`SfBufferAttr_HipcPointer |
  SfBufferAttr_In`). Три другие формы дают `0xf601`.
- `EnableStayHalfAwake` принимает вход шириной ≤ 8 байт (u8/u32/u64 проходят,
  void отвергается).
- `0xf601` = «неизвестная команда, сессия закрыта». Сессию надо пересоздавать
  после каждого отказа, иначе один неверный id убивает все последующие вызовы.

## 5. Три индикатора, которые врут

| Индикатор | Что показал | Что было на самом деле |
|---|---|---|
| `WillStayHalfAwakeInsteadSleep` | 0 перед сном | half-awake случился девять раз |
| `NET_UP` (состояние nifm-запроса) | «соединения нет» во всех окнах | через него шло 2.4 MB/s |
| `rc=0` от `EnableStayHalfAwake` | «принято» | принималось и когда half-awake был запрещён настройкой |

Единственный достоверный признак окна — **`IsInHalfAwake`** (cmd 4 на
`ITaskService`).

## 6. Инженерные требования к демону

Всё выведено из наблюдений, а не из общих соображений.

1. **Пересоздавать слушающий сокет после каждого пробуждения.** Сон уничтожает
   листенер и не возвращает его: порт был refused, пока процесс спокойно
   сэмплировал.
2. **Переподавать nifm-запрос после пробуждения** — `NifmRequestState`
   откатывается в 1 и больше не `Available`.
3. **Не регистрировать сокеты через `RegisterSocketDescriptor`** — см. §2.
4. **Никакого блокирующего I/O в потоке, который должен мерить или планировать.**
   Сэмплер зонда замирал ровно на 60 сэмплах, пока DBI держал SD; измерение,
   ради которого всё затевалось, происходит именно тогда, когда fs недоступна.
5. **Свой буфер на поток.** bsd отдаёт адрес вызывающего драйверу; параллельные
   `recv` на один адрес дают EFAULT.
6. **`sb_efficiency` не меньше 4.** С 2 (как в `SYSMODULE_PLAN.md` §2) четыре
   качающих сокета исчерпывали пул: loopback давал ENOBUFS, управляющие
   соединения получали RST.
7. **`setsysGetFirmwareVersion` + `hosversionSet` вручную в `__appInit`.** Иначе
   libnx считает прошивку 0.0.0 и молча отключает все `[3.0.0+]`-функции,
   возвращая `0x4b59` (модуль 345 / ошибка 37 `LibnxError_IncompatSysVer`).
8. **`min_kernel_version` в `kernel_capabilities`** — без неё ядро не создаёт
   процесс: модуль висит `off`, крашрепорта под TID нет вообще. `npdmtool` эту
   capability не добавляет и молчит.
9. **Проверять `GetOperationMode` на старте** и объяснять пользователю
   `enable_halfawake=0`.

## 6b. Окна пропадают, и лечится это перезагрузкой (2026-07-31)

Шесть прогонов на HOS 22.5.0, питание одинаковое (`battery=100 charger=2`).
Первые пять — на консоли, которая работала без перезагрузки с 29 июля и за это
время пережила установку демона, выгрузку пяти чужих сисмодулей и полтора
десятка циклов сна:

| # | конфигурация | окна | глухой провал |
|---|---|---|---|
| 1 | `stay=0 task=0 schedule=0` | 1 | 612 с |
| 2 | `stay=1` | 1 | 633 с |
| 3 | `stay=1 task=1 schedule=30` | 2 | 951 с |
| 4 | `stay=1 task=1` | 1 | 707 с |
| 5 | то же + `kept_in_sleep=1` | 1 | 695 с |
| **6** | **та же, что 5, но после перезагрузки** | **11** | — |

Прогон 6: 793 с сна, **564.9 MiB, в среднем 0.75 MB/s**, скважность 35%, окна
15–70 с, интервалы между ними 1–122 с. Это лучше базового прогона 29 июля
(0.64 MB/s, 282 MiB за 441 с).

**Вывод: консоль приходит в состояние, в котором half-awake не выдаётся вообще,
и выводит её оттуда только перезагрузка.** Во всех пяти испорченных прогонах
картина одна: одно окно 15 с на переходе в сон, дальше 600–950 с без единого
кванта CPU и без единого байта.

Чем именно она в это состояние приходит — **не установлено**. Кандидаты:
накопленные циклы сна, загрузка/выгрузка сисмодулей, запуск демона. Это риск
для всей фичи, а не курьёз: если состояние копится за сутки работы, ночная
загрузка будет молча не работать. Померить надо отдельно — сколько циклов сна
или часов аптайма до отказа.

### Что из-за этого пришлось отозвать

- **Прогоны 1–5 недействительны.** Они мерили сломанную консоль, а не разницу
  между конфигурациями, поэтому вопрос «какой из вызовов bgtc открывает окна»
  (§7 №1) остаётся **открытым**: его надо переставить, перезагружаясь перед
  каждым прогоном.
- **`WillStayHalfAwakeInsteadSleep` (cmd 103) как предиктор не работает.** В
  прогоне 6 он возвращал `will=0` на всём протяжении, включая моменты внутри
  настоящих окон. Написанное выше «предикат правильно предсказал исход ещё до
  засыпания» — совпадение одного прогона. Дешёвой замены сну нет: проверять
  можно только сном.
- **`kept_in_sleep` в `probe.ini` управлял не тем, чем сказано.** Регистрация
  сокета 0 (`socketNifmRequestRegisterSocketDescriptor`) шла безусловно, ключ
  выключал только `nifmRequestSetKeptInSleep`. Разведено на два ключа:
  `kept_in_sleep` (флаг на nifm-запросе) и `kept_socket` (регистрация сокета).
- Инструмент врал молча: строка `battery=/charger=/will=` печаталась «раз в 60
  сэмплов», а во сне сэмпл идёт только внутри окна, поэтому в прогонах на 44–56
  сэмплов она не напечаталась ни разу — ровно там, где была нужна. Теперь
  печатается на каждом переключении `IsInHalfAwake`.

## 7. Что делать дальше

### Немедленно: переписать планы

- `SYSMODULE_PLAN.md` **§0.3** — «загрузка во сне невозможна» опровергнуто
  замером. Переписать вместе с §7.
- `SYSMODULE_PLAN.md` **§3 удалить целиком.** IPC-протокол не пишем: H8
  положительна межпроцессно (`verdict: loopback=yes lan=yes`), демон поднимает
  `WebServer`, приложение и оверлей — HTTP-клиенты. Исчезает целая фаза.
- `SYSMODULE_PLAN.md` **§2** — `sb_efficiency 2` заменить на 4; 12 пиров в тот
  бюджет тем более не влезали.
- `ESHOP_APPLET_PLAN.md` **§5.4** — прав по существу («вердикт не опровергнут, а
  лишён обоснования»), но неверен в номерах команд: 103 и 200 живут не там, где
  указано, а `EnableStayHalfAwake` сам по себе окна не открывает.

### Незакрытые вопросы, по убыванию цены

0. **Отчего консоль перестаёт выдавать окна** (см. §6b). Теперь это вопрос
   номер ноль: он бьёт по фиче целиком, а не по её потолку. Мерить числом
   циклов сна или часов аптайма до отказа.
1. **Чем вызываются окна?** В измеренном прогоне одновременно вызывались
   `EnableStayHalfAwake`, `NotifyTaskStarting` и `ScheduleTask(60)`; интервалы
   20–113 с подозрительно близки к запрошенным 60. Надо развести: система даёт
   окна сама или их заказала наша задача. От этого зависит, сможет ли демон
   **заказывать** окна, а не ждать их — то есть потолок скорости во сне.
   Проверяется тремя прогонами с разными комбинациями (ключи `bgtc_stay`,
   `bgtc_task`, `bgtc_schedule`), сон обязателен, **и перезагрузка перед
   каждым** — иначе меряется §6b, а не конфигурация.
2. **E4: сон из запущенной игры.** Половина смысла фичи именно там, и это
   единственный непроверенный сценарий Ф2/Ф3.
3. **E3: 10 минут под игрой.** H6 — пропускная способность и поведение игры.
4. **H3: `psc`.** Ни один прогон не шёл с `psc=1`. Демону psc нужен, чтобы знать
   о засыпании; риск — незакрытый ack задерживает засыпание всей консоли, и
   поэтому это стоит проверять последним и с `psc=0` наготове в конфиге.
   Побочно: по switchbrew состояние `PmState` №1 называется **`MinimumAwake`**
   (libnx зовёт его `PscPmState_ReadyAwaken`) — вероятно, это и есть half-awake
   на уровне psc, то есть второй независимый индикатор окна.
5. **Установка на NAND через `ncm`** — E7 проверил только SD. Следующий шаг по
   установке во сне: placeholder + запись по офсету + `Register`, всё внутри
   окна, с честной остановкой на границе.
6. **Почему поток 0 не восстанавливается в окне** (см. поправку к §2).
7. **`GetTriggerEvent` (cmd 3).** Если он сигналит на входе в окно, демон может
   ждать событие вместо опроса `IsInHalfAwake` раз в секунду.

### Чего в зонде намеренно нет и почему

- **Движка.** Смешивать «bsd не работает в sysmodule» с «не влезает
  piece-буфер» — значит не получить ответа ни на то, ни на другое.
- **curl/mbedtls.** Главный риск `SYSMODULE_PLAN.md` §5, но его дешевле обойти,
  чем проверить: UDP-трекеры и DHT уже без curl, HTTP-анонс — plain GET на
  полсотни строк.
