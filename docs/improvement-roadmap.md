# Роадмап улучшения pipensx

Дата исследования: **23 сентября 2026**. База: локальный `main`, коммит
`fd1d4441117c7cc6bf63313bae9b085421fa9d23`. На момент проверки последний
опубликованный стабильный релиз — [1.6.2](https://github.com/i3sey/pipensx/releases/tag/1.6.2);
в исследуемом коде ещё 10 коммитов после его тега. Выводы о коде ниже относятся
к этой базе, а не автоматически к установленной у пользователя версии.

Цель — сбалансированно улучшить надёжность, UI/UX на Switch, возможности
приложения, веб-интерфейс и качество разработки. **Раздача, сидирование,
upload ratio и связанные функции исключены.**

Это результат чтения исходников, тестов, README/BUILD, открытых GitHub Issues
с комментариями и ряда закрытых задач. Приложение на физической Switch в ходе
исследования не запускалось; фотографии из issues не декодировались.
Предложения по визуальному удобству требуют проверки на устройстве.

## 1. Что делать в первую очередь

1. Разобрать падение из #86 и определить затронутые версии и сценарии.
2. Исправить перерисовку прогресса подготовки и доступность команд в обоих UI.
3. Вернуть понятную очистку истории прямо в Downloads, отдельно от удаления данных.
4. Согласовать выбор источника между Switch и Web Companion.
5. Сделать ошибки, восстановление и итог установки понятными без чтения логов.

После этого развивать поиск и каталог, управление очередью и местом,
ограничение скорости, доступность и производительность. Это не требует
переписывания приложения: значительная часть нужных механизмов уже существует.

### Обозначения

- **Код** — поведение или рассогласование подтверждено чтением текущей реализации.
- **Локально** — дополнительно вызваны реальные JS-функции вне браузера.
- **Репорт** — сообщение пользователя; причина и актуальность ещё не установлены.
- **Предложение** — улучшение продукта, а не утверждение о существующем баге.
- **P0** — срочное исследование потенциального падения/потери данных;
  **P1** — основной сценарий нарушен или вводит в заблуждение;
  **P2** — заметное улучшение; **P3** — развитие после базовых исправлений.
- **S / M / L** — небольшой локальный объём / несколько компонентов /
  существенное изменение с отдельной проверкой на устройстве. Это относительные
  оценки, не обещание сроков. Для неизвестной причины указана оценка исследования.

## 3. Что уже сделано и не должно снова становиться «новой фичей»

В проекте уже есть постоянная очередь, pause/resume/retry/recheck, несколько
параллельных загрузок, Smart Install, выбор файлов, пакетная подготовка,
проверка места, управление хранилищем, удаление установленных приложений,
поиск обновлений игр, избранное, фильтры каталога, экран Home, Web Companion,
настройка с телефона, QR-отчёты, темы и несколько языков. Поддерживаются
TorBox, Real-Debrid, TorrServer и AllDebrid в исследуемой базе.

Основание: [README](../README.md), [UI](../src/ui/),
[сервисы приложения](../src/app/). Home пока выключен по умолчанию
(`showHomeTab = false` в [настройках](../src/app/app_settings.hpp)).
Проверка UI не должна предполагать, что пользователь вообще открывал Home.

CI уже запускает PC-тесты, ASan/UBSan, fuzz smoke для bencode/metainfo,
Switch-сборку и gitleaks. Проверка переводов вызывается из `Makefile.pc test`.
Задача — расширить покрытие пользовательских сценариев, а не «добавить CI».
См. [workflow](../.github/workflows/ci.yml), [Makefile.pc](../Makefile.pc).

## 4. Надёжность и подтверждённые рассогласования

### R01. Падение консоли: воспроизведение и защита от регрессий

**P0 на исследование · Репорт #86 · M на диагностику, исправление пока не оценено.**

Собрать точную версию/commit, режим запуска, источник, фазу сбоя, crash report,
размер piece, число активных задач и доступную память. Воспроизвести на
безопасном тестовом содержимом; отдельно проверить чистую и существующую очередь.
Сопоставить с исправлениями #81, не считать их причиной или решением #86 заранее.

Готово, когда есть воспроизводимый сценарий и проверенное исправление либо
обоснованная локализация причины вне приложения с конкретными доказательствами.
После исправления: повтор исходного сценария, длительная загрузка с установкой,
проверка очереди после перезапуска; результаты с указанием устройства и сборки.

### [x] R02. Процент подготовки меняется в модели, но список может не обновляться

**P1 · Код · S.**

В [MainView::refresh](../src/ui/downloads/downloads_view.hpp) решение о
перерисовке не сравнивает `fetchProgress`. При этом
[DownloadCell::setTask](../src/ui/downloads/download_cell.hpp) выводит этот
процент для `Fetching`, а `runDebridTask` обновляет поле через `onProgress`
в [менеджере](../src/app/download_manager.cpp).
Если меняется только `fetchProgress`, родитель выходит раньше обновления строки.
Пользователь может принять подготовку на сервере за зависание.

Включить все отображаемые поля в критерий обновления либо использовать
ревизию состояния отображения. Проверить также `error`, размеры и число пакетов,
которые строка читает, а внешний фильтр обновления учитывает не полностью.

Готово: последовательность `Fetching 10% → 40% → 90%` при неизменных остальных
полях видна без перехода между вкладками; фокус и прокрутка не сбрасываются.
Тест должен проверять обновление через родительский экран, а не только ячейку.

### [x] R03. Команды UI должны соответствовать возможностям задачи

**P1 · Код + Локально · M.**

[Web taskCard](../resources/web/app.js) предлагает Verify для `Paused`, `Error`
и `Completed`, но [DownloadManager::verify](../src/app/download_manager.cpp)
принимает только `Completed` и отказывает debrid-задачам. В Switch-меню и
[DetailsActivity::updateButtons](../src/ui/downloads/details_activity.hpp)
проверяется завершённость, но не `TaskSource::Debrid`.
Получается доступная кнопка, которая заведомо не может выполнить действие.

Есть и другие расхождения: веб-карточка не предлагает индивидуальную паузу
для ряда состояний, которые менеджер принимает; одиночная и массовая пауза
по-разному относятся к `Committing`. Последнее требует явного решения о
безопасной границе, а не механического расширения списка состояний.

Ввести общую модель доступных действий с причиной недоступности: `canPause`,
`canResume`, `canVerify`, `canRemove`, `canMove`. Учитывать источник, фазу и
lease копирования. Отдавать результат в API и использовать в UI Switch.
Менеджер всё равно повторно проверяет команду: состояние может измениться.

Готово: для каждого сочетания статуса/источника оба UI показывают одинаковые
возможности; Verify не предлагается debrid; гонка состояния даёт понятный
ответ и обновляет карточку. Сценарии покрыты таблицей тестов.

### [x] R04. Очистка списка, удаление файлов и удаление игры — разные действия

**P1 · Код + Репорт #85 · S–M.**

В [Downloads](../src/ui/downloads/downloads_view.hpp) есть поштучное удаление,
но нет массовой очистки истории. В
[StoragePanel::clearCompleted](../src/ui/settings/settings_panels.hpp)
вызывается `clearCompleted(true, ...)`, то есть с удалением данных;
[веб-кнопка](../resources/web/app.js) отправляет `deleteData: false`.
Таким образом, на Switch функция не исчезла целиком, но действие и его
местоположение отличаются от ожидаемых.

Добавить в Downloads «Очистить завершённые записи» с количеством задач.
Отдельно предлагать очистку скачанных файлов с объёмом освобождения.
В тексте явно объяснять, что происходит с установленными играми и портами;
не называть очистку истории удалением игры. Результат должен сообщать,
сколько задач обработано и сколько пропущено из-за занятого состояния.

Готово: очистка истории доступна с геймпада и touch прямо в Downloads,
включая скрытые завершённые задачи; режим сохранения файлов их не меняет;
активные и leased-задачи сохраняются. Удаление установленных приложений
остаётся отдельным явно названным действием.

### [x] R05. Единый путь добавления через выбранный источник

**P1 · Код + Репорт #75 · L.**

[WebAddQueue::runJob](../src/app/web_add_queue.cpp) прямо блокирует добавление
при выключенном `torrentingEnabled` и сообщает об отсутствии собственного
debrid-пути. Каталог и magnet из [WebServer](../src/app/web_server.cpp)
попадают именно сюда. Поэтому выбор TorrServer/debrid в настройках не делает
тот же релиз доступным для добавления с телефона.

Выделить общий сервис подготовки/добавления задачи для консоли, пакетной
установки и веба. Использовать сохранённый источник и его возможности;
не включать Direct BitTorrent автоматически как обход ошибки. Сначала
обеспечить паритет добавления из каталога, затем явно определить поддержку
произвольных magnet и `.torrent` каждым источником.

Готово: один релиз с Switch и телефона использует одинаковый источник,
режим и выбор файлов. Неподдерживаемый вариант объясняется до постановки
задания. Тесты охватывают Direct и все четыре провайдера с подменёнными ответами.

### R06. Проверяемое восстановление после паузы, Power и обрыва

**P1 · Репорт #72; механизмы восстановления уже есть · L.**

В менеджере есть периодические checkpoint примерно раз в пять секунд,
восстановление bitfield и отдельный учёт прогресса. В
[test_manager](../tests/test_manager.cpp) уже проверяются сохранение и загрузка
состояния. Это не доказательство исправной работы всех фаз на устройстве.

Разделить в интерфейсе «скачано», «установлено» и «проверяем сохранённые данные».
Если приходится повторно читать/получать часть текущего пакета, объяснять это
и показывать сохранённые результаты. Не обещать точное продолжение с любого
байта для всех форматов и источников.

Готово: матрица pause/resume, перезапуск, сон/пробуждение и потеря сети
проверена для Direct/debrid, DownloadOnly/StreamInstall/PortInstall и фаз
подготовки/загрузки/установки. Уже завершённые пакеты не устанавливаются заново;
необходимая повторная работа измерена и отражена в UI. Запись состояния
и фактическое восстановление проверяются отдельно от красивого процента.

### R07. Ошибка должна объяснять следующий шаг

**P1 · Код + Репорты #76/#77 · M–L.**

Сейчас [DetailsActivity](../src/ui/downloads/details_activity.hpp) показывает
строку `task.error`; QR-отчёт открывается через отдельные экраны.
Добавить структурированный код ошибки, фазу, возможность повтора и действие:
повторить, открыть источник, проверить сеть, освободить место, показать отчёт.
Исходное сообщение сохранить в технических подробностях.

Для TLS различать DNS/connect, handshake и проверку сертификата. Не сводить
любой `SSL connect error` к неверной дате: #77 прямо показывает слабость такого
совета. Автоповтор ограничить временными ошибками с задержкой и пределом;
авторизацию, нехватку места и повреждённый пакет не повторять бесконечно.

Готово: типовые ошибки дают локализованное объяснение и работающую кнопку;
попытки и время следующего повтора видны; отмена работает. Сбор отчёта из
ошибочной задачи сохраняет её идентификатор и фазу, не раскрывая ключи.

## 5. UI/UX и развитие возможностей

### R08. Видимый поисковый запрос и управляемые фильтры

**P2 · Код + Предложение · S–M.**

В [CatalogView](../src/ui/catalog/catalog_view.hpp) поиск представлен иконкой
с пустым текстом; `updateHeader()` меняет её цвет и показывает Reset, но не
выводит сам запрос. Пользователь видит отфильтрованный каталог без текста,
который его ограничивает.

Показывать запрос чипом «Поиск: …», отдельно сбрасывать поиск и все фильтры,
сохранять состояние при возврате из карточки. Добавить историю последних
запросов и понятный empty state с предложением снять конкретный фильтр.
Проверить ширину панели: несколько неужимаемых чипов и длинные переводы могут
потребовать меню «Фильтры», а не ещё одного постоянного чипа.

Готово: запрос и активные ограничения читаются без повторного открытия
клавиатуры; сброс доступен с touch и контроллера; длинный русский/французский
текст не вытесняет поиск. Проверка переполнения — на реальном UI, не по коду.

### R09. Понятный бюджет места для всей очереди

**P2 · Предложение на основе существующих оценок · L.**

В [install_space](../src/app/install_space.hpp) уже есть оценки с признаком
точности и раздельная проверка SD/NAND. Пакетная подготовка суммирует объёмы.
Но фильтр каталога [fitsOnly](../src/app/catalog_presentation.cpp) сравнивает
размер раздачи с текущим свободным местом; неизвестный размер не скрывает.
Это приблизительная фильтрация, не гарантия, что установка поместится.

Объяснить смысл фильтра и добавить общий прогноз очереди: скачанные данные,
распакованный контент, временный запас, выбранное хранилище и уже обещанный
очереди объём. Использовать существующую оценку, не дублировать формулы.
Перед стартом повторно проверять место; при неизвестном размере показывать
неопределённость и предлагать подготовку оценки.

Готово: две задачи, каждая из которых отдельно помещается, не получают
безусловное обещание совместной установки; учтены сжатие и SD/NAND.
При нехватке места доступен переход к подходящей очистке с возвратом к задаче.

### R10. Итог установки и объяснение дополнительных файлов

**P2 · Предложение · M.**

Smart Install и обработка портов/дополнений активно развиваются; последние
коммиты уже исправляют выбор extras и сообщения о пропуске. Не начинать
реализацию этой поддержки заново. Расширить существующие
[выбор файлов](../src/ui/detail/torrent_selection.hpp) и
[просмотр файлов задачи](../src/ui/downloads/task_files_activity.hpp).

Добавить доступный после завершения итог: установленные пакеты, скопированные
файлы и назначения, пропущенные файлы с причинами, предупреждения и оставшиеся
скачанные данные. Предварительный экран использует те же понятия, что итог.
Для долгой финализации показывать её название, а не только неподвижные 100%.

### R19. Веб-диагностика и контракт API

**P2 · Код + Локально + Предложение · M.**

Дополнительно формализовать проверку входного JSON: часть обработчиков вызывает
`body.value` без проверки типа поля; исключение ловится HTTP-сервером и становится
500. Неверный тип пользовательского ввода должен давать 400 с понятной причиной.
Это замечание о корректности API, а не утверждение о падении приложения.

Приватность — отдельное продуктовое решение: сейчас GET tasks/events/storage
не требует PIN, а mutations и settings защищены. Это существующая политика,
не обход установленной защиты. Объяснить её в настройках и рассмотреть режим
закрытого просмотра; при его реализации отдельно решить авторизацию SSE.

Готово: debrid не получает советы про peers; некорректный JSON не превращается
во внутреннюю ошибку; документация точно описывает доступ к данным в LAN.
Браузер после разрыва соединения показывает устаревшие данные как устаревшие,
а после восстановления получает актуальное состояние без дубликатов действий.

## 7. Порядок реализации

Этапы задают порядок и критерий перехода, а не календарные обещания.
В каждом этапе есть пользовательское улучшение и проверка надёжности.

| Этап | Состав | Результат / условие перехода |
| --- | --- | --- |
| A — ближайший набор исправлений | R01: диагностика; R02; R03; R04; R18: тесты этих сценариев; R20: точная версия в репортах | Прогресс и команды соответствуют состоянию; очистка доступна; для #86 есть обоснованный статус и следующий проверяемый шаг. Обычные UI-фиксы не ждут бесконечно внешнего воспроизведения. |
| B — предсказуемая загрузка | R05; R06; R07; R12; R19: источник и health | Switch и телефон используют выбранный метод, ошибки дают действие, восстановление проверено. Выпуск изменения восстановления требует проверки на устройстве. |
| C — удобство повседневного использования | R08; R09; R10; R11; R14; R17 | Пользователь понимает выбор, место, очередь и результат; основные сценарии проверены с touch и геймпадом. |

у неё существенно больший риск, чем у этих локальных исправлений.

## 8. Проверка результата

### Регрессионная матрица

| Измерение | Минимальный набор |
| --- | --- |
| Источник | Direct, TorrServer, TorBox, Real-Debrid, AllDebrid; ответы сервисов подменяются в автоматических тестах |
| Режим | Только скачивание, stream install, порт/копирование extras |
| Фаза | Queued, Checking, Fetching, Downloading, Installing, Committing, terminal states, внешний lease |
| Прерывание | Пауза, перезапуск, потеря сети, сон/пробуждение на Switch |
| Место | Достаточно, недостаточно, неизвестно, изменение после постановки в очередь; SD и NAND |
| UI | Контроллер, touch, handheld/docked, светлая/тёмная тема, длинные переводы, мобильный браузер |

Это оси покрытия, не требование тестировать полное декартово произведение.
Для конкретного изменения выбирать затронутые сочетания; для релиза обязательно
повторять ранее воспроизведённые регрессии и основные сквозные сценарии.

При изменении shared/core выполнять `make -f Makefile.pc test` и затронутую
сборку; для Switch — `make switch`, для CLI — `make pc`.
Переводы должны проходить `scripts/check_i18n.py`. Для изменений установщика,
libnx и формата состояния использовать соответствующие инструкции репозитория.
PC-проверка не подтверждает сон/пробуждение и корректность установки на устройстве.

### Как измерять улучшение

- Надёжность: число ошибок/падений на фиксированном наборе контрольных операций;
  сколько данных приходится повторно обрабатывать после прерывания.
- UX: время и число действий для очистки истории, восстановления после ошибки,
  поиска релиза и настройки источника; доля успешно пройденных сценариев.
- Производительность: время первого содержимого каталога, p95 задержки поиска
  и кадров, пик памяти, скорость на одинаковом источнике и карте.
- Поддержка: сколько репортов сразу содержат точную сборку и воспроизводимый
  сценарий; сколько закрытий подтверждены на релизе с исправлением.

Начальные значения в этом исследовании не измерялись. Сначала снять baseline,
затем назначить численные цели. Достаточно локальных измерений и добровольных
отчётов; скрытая отправка телеметрии для этого не нужна.
